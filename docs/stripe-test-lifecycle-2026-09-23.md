# Stripe sandbox handler verification — 23 September 2026

This was a Stripe **test-mode** handler acceptance run. It did not use live
payments. The test used `sk_test_...`, Stripe's `tok_visa`, and a profile
automatically classified as a test account.

The distinction matters:

- Stripe's API genuinely created the customer, payment method, subscription,
  subscription updates, Billing Portal session, and cancellation.
- The script then **constructed and signed webhook payloads locally** for
  `checkout.session.completed`, `invoice.paid`, `invoice.payment_failed`,
  `customer.subscription.updated`, and `customer.subscription.deleted`.
- Those local payloads verify webhook signature handling, business rules,
  idempotency, and ledger effects. They do **not** prove that Checkout, Stripe's
  renewal engine, failed-payment collection, or the Billing Portal generated and
  delivered those lifecycle events end to end.

Handler cases verified with simulated signed webhooks:

- A simulated paid Starter signup created the application subscription and
  granted one monthly allowance.
- Re-delivering the signup invoice did not grant credits twice.
- A simulated one-time Small top-up granted the configured 1,000 credits.
- Re-delivering the top-up event did not grant credits twice.
- A simulated paid Starter-to-Growth upgrade granted only the 1,500-credit difference.
- A Growth-to-Starter downgrade stayed pending until the next paid cycle.
- A simulated next paid cycle applied Starter and granted the Starter allowance.
- Re-delivering the renewal invoice did not grant credits twice.
- A simulated failed renewal changed the subscription to `past_due` and granted no credits.
- Stripe's API returned a genuine hosted Billing Portal URL with the billing-page return URL;
  no human portal interaction was completed in this run.
- Scheduled cancellation retained access through the paid-through date.
- Final cancellation marked the subscription canceled and expired plan credits.
